DETECTED PROBLEMS (with causes + fixes)

[CRITICAL] Slug update bug (cached slug prevents updates)
- Where:
  - server/services/url-slug.js (URLSlugService.updateSlug -> getSlugForArticle)
  - server/routes/cms.js updates slug on header change via urlSlugService.updateSlug(...)
- Symptom:
  - You edit an article headline (header/title) but its slug often stays the same.
  - Users see old URLs, or multiple headlines share unexpected slugs.
- Why it happens:
  - updateSlug() calls getSlugForArticle(articleId, newTitle)
  - getSlugForArticle() returns early if an entry already exists in NodeCache or slugMap,
    so it does NOT regenerate slug from the new title for existing articles.
- How to solve:
  - Implement a “force regenerate” path. Examples:
    - updateSlug(): explicitly recompute from newTitle (generateSlug + ensureUniqueSlug),
      then overwrite slugMap + NodeCache and persist.
    - OR: delete existing mapping first (slugMap.delete + cache.del) before calling getSlugForArticle.
  - Add automated test: “changing header changes slug” and “slug uniqueness maintained”.

[HIGH] Slug lookup is O(n) per article request (scales poorly)
- Where:
  - server/services/url-slug.js getIdBySlug() loops over slugMap entries
  - server/routes/pages.js /haber/:slug uses urlSlugService.getIdBySlug(slug) on every request
- Symptom:
  - As slug-cache grows (thousands+ articles), article page requests get slower and CPU increases.
- Why it happens:
  - getIdBySlug is a linear scan over all slugs (O(number_of_articles)).
- How to solve:
  - Maintain a reverse index: slug -> articleId (Map) updated whenever slugMap changes.
  - Alternatively store slugs in SQLite with an index and query by slug.

[HIGH] Slug normalization missing for /haber/:slug (Turkish/URL-encoded edge cases)
- Where:
  - server/routes/pages.js: uses getIdBySlug(slug) directly
  - url-slug service provides normalizeSlugFromUrl(), but it isn’t used here
- Symptom:
  - Some URLs with URL-encoded Turkish characters or unexpected casing don’t resolve (404).
- Why it happens:
  - Category routes normalize; article route does not.
- How to solve:
  - Normalize incoming slug parameter before lookup (normalizeSlugFromUrl).
  - Consider redirecting to canonical slug (301) when normalized differs (SEO consistency).

[HIGH] Slug cache persistence is expensive and can corrupt under concurrency
- Where:
  - server/services/url-slug.js saveSlugCache() writes whole JSON (`slug-cache.json`) with pretty print
  - worker + server both can read/write slug-cache.json
- Symptoms:
  - “Slow slug update” during bulk ingestion / high write rate (disk I/O + JSON stringify).
  - Risk of partially-written/corrupted JSON if two processes write around the same time.
- Why it happens:
  - Each new slug triggers a full file rewrite.
  - There’s no file lock and no atomic “write temp then rename” pattern.
- How to solve:
  - Make writes atomic: write to temp file then rename.
  - Add file locking, or serialize writes, or batch updates (debounce / coalesce).
  - Prefer moving slug storage into SQLite with an indexed table (authoritative source).

[HIGH] “Manşet / Carousel” inconsistency (two sources of truth)
- Where:
  - Manual ordered list: data-service “carousel_layout” table:
    - server/services/data-service.js: getCarouselArticles(), updateCarouselLayout(), etc.
  - Target membership: articles.targettedViews (JSON text):
    - server/services/data-service.js getArticles({ targettedView }) uses LIKE on targettedViews
  - CMS:
    - server/routes/cms.js dashboard initialState: prefers manual carousel list first
    - BUT GET /cms/carousel returns targettedView-based list (date-sorted)
    - PUT /cms/carousel saves manual list to carousel_layout
  - Frontend CMS JS:
    - public/cms/js/cms-app.js loadHeadlineLayout() fetches /cms/carousel and repaints table
- Symptom:
  - You reorder “Manşet Slider” in CMS and hit save, but refresh/return shows different order.
  - Homepage can show a different carousel from what CMS “carousel” API returns.
  - “Slow / inconsistent manşet update” perception: because multiple pipelines touch carousel.
- Why it happens:
  - There are two independent mechanisms controlling carousel content:
    - carousel_layout (manual order) vs targettedViews membership.
  - CMS GET endpoint serves one mechanism (targettedViews), while CMS PUT endpoint writes the other (carousel_layout).
- How to solve:
  - Pick ONE authoritative model and align:
    - Option A (recommended): carousel_layout is authoritative for carousel membership + order.
      - Make GET /cms/carousel return dataService.getCarouselArticles() in stored order.
      - Ensure “add/remove carousel” operations update carousel_layout (and optionally also set targettedViews for analytics).
    - Option B: remove carousel_layout entirely and store order in DB (explicit ordering column or join table).
      - Then homepage and CMS both read from the same ordering store.
  - Add regression tests: “save order persists” and “homepage equals CMS preview list”.

[MED/HIGH] TargettedViews stored as JSON text + LIKE filtering (performance and correctness)
- Where:
  - server/services/data-service.js getArticles: `targettedViews LIKE '%"carousel"%'`
- Symptoms:
  - Queries get slower as DB grows (no index use).
  - Potential false positives if target strings overlap (less likely due to quoting, but still brittle).
- How to solve:
  - Normalize to a join table (article_id, target) with indexes.
  - Or use SQLite JSON1 (json_each) + indexing strategy if available.

[HIGH] Hardcoded Master Admin fallback credentials
- Where:
  - server/routes/auth.js: defaults to username 'admin', password 'admin123' if env vars absent
- Symptom:
  - If deployed without env hardening, anyone can log in as admin.
- Why it happens:
  - Intended for dev convenience, but the fallback exists unconditionally.
- How to solve:
  - In production: require env vars and refuse to start if missing.
  - Alternatively restrict fallback to NODE_ENV=development only.
  - Add rate limiting and lockout policies for /api/auth/login.

[HIGH] Weak default session secret
- Where:
  - server/index.js: `secret: process.env.SESSION_SECRET || 'uha-secret-key-change-in-prod'`
- Symptom:
  - Predictable session signing key if SESSION_SECRET isn’t set => session forgery risk.
- How to solve:
  - Require SESSION_SECRET in production and rotate secrets.
  - Consider setting cookie `sameSite` explicitly and verifying HTTPS/proxy settings.

[HIGH] RSS subscription URL/token committed to repo
- Where:
  - workers/dha-rss-worker.js (SETTINGS.defaultFeedUrl)
  - tests also contain the same URL
- Symptom:
  - Secret leakage: anyone with repo access can use/abuse the RSS subscription.
- How to solve:
  - Move feed URL into environment variables or secret manager.
  - Rotate/revoke existing token.
  - Keep test fixtures sanitized (use sample RSS dump, not live secret URL).

[HIGH] XSS risk: rendering raw HTML via `| safe` while ingesting external HTML
- Where:
  - templates/pages/article.njk and templates/widgets/article-content.njk: `{{ article.content | safe }}`
  - workers/dha-rss-worker.js: stores `body: descriptionHtml` (raw RSS HTML) into DB
- Symptom:
  - Malicious HTML in RSS (or CMS content) can execute scripts in users’ browsers.
  - CSP currently includes 'unsafe-inline' in scripts/styles, which increases blast radius.
- How to solve:
  - Sanitize HTML on ingestion (RSS worker + CMS save) using an allowlist sanitizer.
  - At minimum strip script tags + inline event handlers + javascript: URLs.
  - Tighten CSP to remove 'unsafe-inline' where possible (use nonces/hashes).

[MED] CORS is wide open by default
- Where:
  - server/index.js: app.use(cors())
- Symptom:
  - Broad exposure of API endpoints; increases attack surface.
- How to solve:

- Where:

  - If directly exposed to the internet, clients can spoof X-Forwarded-* headers.
  - This can affect protocol detection (req.secure), cookies, and security decisions.
- How to solve:
  - Set trust proxy to a strict value (e.g., 1 hop) or trusted IP ranges.
  - Make it environment-configurable and default to false unless explicitly behind a proxy.

[MED] Worker scheduler executes shell command strings with `shell: true`
- Where:
  - server/index.js startWorker(): spawn(command, { shell: true })
- Symptom:
  - If an attacker can influence env vars, this becomes command injection.
- How to solve:
  - Avoid shell mode; pass executable + args array; validate command inputs.

[MED] Excessive synchronous logging and file writes in CMS routes
- Where:
  - server/routes/cms.js:
    - Logs every CMS request (console.log)
    - Layout save endpoints append to layout-changes.log using fs.appendFileSync
- Symptom:
  - Event loop blocking under usage, slow CMS actions, log bloat.
- How to solve:
  - Gate debug logging behind NODE_ENV/flag.
  - Use async logging and structured logger with rotation.

[MED] Sitemap/Robots and “pageUrl” ignore BASE_PATH
- Where:
  - server/services/sitemap.js uses config.getSiteUrl(req) only (no base path)
  - server/routes/pages.js sets pageUrl = `${siteUrl}/haber/${slug}` (no base path)
- Symptom:
  - If deployed under a subpath (BASE_PATH), generated URLs are wrong.
- How to solve:
  - Use a single helper (e.g., config.getUrl(req, '/haber/...')) that includes basePath.
  - Apply same logic to robots.txt and RSS self links.

1. SLOW SLUG UPDATE PROBLEM
───────────────────────────────────────────────────────────────────────────────
Location: server/services/url-slug.js
Status: CRITICAL

Problem Description:
The slug cache is loaded only once when the server boots. When the RSS worker
(or any external process) adds new articles and generates new slugs, the
running server does NOT see these changes until it is restarted.

Why This Occurs:
- In url-slug.js constructor (line 18): loadSlugCache() reads from disk once
- The slugMap is stored in memory as a Map object
- RSS worker writes to disk but cannot notify the server
- No hot-reload or cache invalidation mechanism exists

Technical Impact:
- New articles ingested via RSS worker return 404 errors
- Users cannot access newly published content without server restart
- Manual intervention required after every RSS ingestion
- Poor user experience and operational overhead

Solution:
Option A - Add a reload endpoint:
  1. Add method: reloadSlugCache() in url-slug.js
  2. Create endpoint: POST /api/cache/reload-slugs
  3. RSS worker calls this endpoint after successful ingestion
  4. Server reloads slugMap from disk on demand

Option B - Implement file watching:
  1. Use fs.watch() or chokidar to monitor slug-cache.json
  2. Automatically reload when file changes detected
  3. Debounce reloads to avoid excessive I/O

Option C - Use shared cache (Redis/Memcached):
  1. Replace JSON file with Redis cache
  2. All processes read/write to shared cache
  3. Eliminates process isolation issues
  4. Better for production scalability

Recommended: Option A for immediate fix, Option C for long-term solution.

6. CONCURRENT FILE ACCESS RACE CONDITION
───────────────────────────────────────────────────────────────────────────────
Location: server/services/url-slug.js (saveSlugCache method)
Status: HIGH

Problem Description:
When multiple processes (server + RSS worker) write to slug-cache.json
simultaneously, the file can become corrupted. No locking mechanism exists
to prevent concurrent writes.

Why This Occurs:
- Line 38-48: saveSlugCache() writes directly to file
- No file locking implemented
- No atomic write pattern (write to temp, then rename)
- Multiple processes can call this simultaneously

Technical Impact:
- Corrupted JSON file breaks all slug lookups
- Server fails to start after corruption
- Lost slug mappings
- Manual recovery required

Solution:
1. Implement atomic writes:
```javascript
async saveSlugCache() {
  try {
    const cacheDir = path.dirname(this.slugCachePath);
    await fsPromises.mkdir(cacheDir, { recursive: true });

    const cache = Object.fromEntries(this.slugMap);
    const tempPath = `${this.slugCachePath}.tmp`;
    
    // Write to temp file
    await fsPromises.writeFile(tempPath, JSON.stringify(cache, null, 2));
    
    // Atomic rename
    await fsPromises.rename(tempPath, this.slugCachePath);
    
    console.log(`💾 Saved ${this.slugMap.size} slug mappings to cache`);
  } catch (error) {
    console.error('❌ Error saving slug cache:', error);
  }
}
```

2. Use file locking library (proper-lockfile):
```javascript
const lockfile = require('proper-lockfile');

async saveSlugCache() {
  const release = await lockfile.lock(this.slugCachePath);
  try {
    // Write logic here
  } finally {
    await release();
  }
}
```

class MigrationManager {
  constructor(db) {
    this.db = db;
    this.initMigrationTable();
  }

  initMigrationTable() {
    this.db.exec(`
      CREATE TABLE IF NOT EXISTS schema_migrations (
        version INTEGER PRIMARY KEY,
        name TEXT NOT NULL,
        applied_at TEXT NOT NULL
      )
    `);
  }

  getCurrentVersion() {
    const result = this.db.prepare(
      'SELECT MAX(version) as version FROM schema_migrations'
    ).get();
    return result.version || 0;
  }

  runMigrations() {
    const currentVersion = this.getCurrentVersion();
    const migrations = this.getAllMigrations();
    
    for (const migration of migrations) {
      if (migration.version > currentVersion) {
        console.log(`Running migration ${migration.version}: ${migration.name}`);
        migration.up(this.db);
        this.recordMigration(migration);
      }
    }
  }
}

PROBLEM #1: SLOW SLUG UPDATE PROBLEM (Yavaş Slug Güncelleme)
-------------------------------------------------------------------------------
Location: server/services/url-slug.js
Current Model: URLSlugService (Singleton with file-based + in-memory cache)

WHY IT OCCURS:
- The slug cache is loaded ONCE at server startup via loadSlugCache()
- When RSS worker (dha-rss-worker.js) adds new articles, it writes new slugs 
  to disk (server/cache/slug-cache.json)
- The running Express server does NOT reload slug-cache.json
- New articles created by the worker are invisible to the server until restart
- The worker calls urlSlugService.getSlugForArticle() which updates the file,
  but server has its own isolated copy of slugMap in memory

HOW TO SOLVE:
1. Add a public reload method to URLSlugService:
   ```javascript
   reloadSlugCache() {
     this.loadSlugCache();
     this.cache.flushAll(); // Clear NodeCache
   }
   ```

2. After RSS worker completes successfully in server/index.js (around line 349),
   call slugServiceInstance.loadSlugCache() to refresh the cache

3. Alternative: Implement file-watcher on slug-cache.json to auto-reload

4. Better long-term: Move slug storage to SQLite and use same DB connection
