# Slug Caching Overview

This document describes how slug generation and caching currently work in the project as of 2025-12-09.

## Key components

- **`server/services/url-slug.js`** – Singleton service responsible for generating, caching, and looking up slugs.
- **`server/cache/slug-cache.json`** – Persistent JSON file storing `{ articleId: slug }` pairs.
- **`NodeCache` (in-memory)** – Short-lived cache (`stdTTL = 3600`) layered on top of the JSON-backed map to avoid repeated lookups during a single process run.

## Initialization flow

1. When the service is required (either by the Express server or any CLI/worker), the constructor runs immediately.
2. `this.loadSlugCache()` reads `server/cache/slug-cache.json` if it exists:
   - Converts the JSON object into a `Map` (`this.slugMap`) for fast lookups.
   - Logs how many mappings were loaded.
   - If the file is missing or corrupt, it starts with an empty `Map` and writes a fresh file on the next save.
3. `NodeCache` is instantiated and remains in memory for quick `getSlugForArticle()` hits during that process lifetime.

## Generating & saving slugs

When `getSlugForArticle(articleId, title)` is called:

1. Check the in-memory `NodeCache`. If present, return immediately.
2. Check `slugMap` (loaded from disk). If the mapping exists, add it to `NodeCache` and return it.
3. Otherwise:
   - Normalize the title (Turkish character mapping + `slugify`) to generate a base slug.
   - Call `ensureUniqueSlug()` to avoid collisions by appending `-1`, `-2`, etc., if needed.
   - Save the slug into `slugMap` and `NodeCache`.
   - Persist `slugMap` by writing `server/cache/slug-cache.json` (pretty-printed JSON) via `saveSlugCache()`.

Other helper methods (`updateSlug`, `deleteSlug`, `batchUpdateSlugs`) follow the same pattern: mutate `slugMap`, update `NodeCache`, then rewrite the JSON file.

## Lookup flow at runtime

- **Article pages (`/haber/:slug`)**: `server/routes/pages.js` uses `urlSlugService.getIdBySlug(slug)` to translate the URL into an article ID. This call only checks the in-memory `slugMap` – no disk access.
- **Category pages**: similar flow when categories are stored with `slug` strings; the slug service is not used here, but the concept is the same (slugs live in the DB).

Because the slug service keeps all mappings in memory:

- Lookups are fast and don’t hit SQLite.
- Any process (server or worker) has its **own** copy of the slug map.

## Current limitations

- The Express server reads `slug-cache.json` only once when it boots. If another process (e.g., the RSS worker) writes new slugs to disk, the running server does **not** see them until it restarts and re-runs `loadSlugCache()`.
- There is no public API to reload the cache or invalidate entries at runtime.
- The JSON file acts as the source of truth, so corruption or manual edits can break both server initialization and workers until the file is fixed.

## Operational notes

- The RSS worker already calls `getSlugForArticle()` after inserting articles, so the JSON file is always up to date.
- To make newly ingested articles accessible without restarting the server, we need to implement a reload hook (not yet available at the time of writing).
- Keep an eye on disk permissions for `server/cache/slug-cache.json`; the service will log `❌ Error saving slug cache` if it cannot write the file.

This doc should be revisited once a reload mechanism or alternative caching strategy is added. For now, restarting the server is the only way to make it pick up new slug mappings generated by background jobs.
