PROBLEM #1: SLOW SLUG UPDATE PROBLEM (Yavaş Slug Güncelleme)
-------------------------------------------------------------------------------
Location: server/services/url-slug.js
Current Model: URLSlugService (Singleton with file-based + in-memory cache)

WHY IT OCCURS:
- The slug cache is loaded ONCE at server startup via loadSlugCache()
- When RSS worker (dha-rss-worker.js) adds new articles, it writes new slugs 
  to disk (server/cache/slug-cache.json)
- The running Express server does NOT reload slug-cache.json
- New articles created by the worker are invisible to the server until restart
- The worker calls urlSlugService.getSlugForArticle() which updates the file,
  but server has its own isolated copy of slugMap in memory

HOW TO SOLVE:
1. Add a public reload method to URLSlugService:
   ```javascript
   reloadSlugCache() {
     this.loadSlugCache();
     this.cache.flushAll(); // Clear NodeCache
   }
   ```

2. After RSS worker completes successfully in server/index.js (around line 349),
   call slugServiceInstance.loadSlugCache() to refresh the cache

3. Alternative: Implement file-watcher on slug-cache.json to auto-reload

4. Better long-term: Move slug storage to SQLite and use same DB connection

PROBLEM #2: MANŞET (Headline) SYNC PROBLEM
-------------------------------------------------------------------------------
Location: server/services/data-service.js (getHeadlineListArticles, addArticleToHeadlineList)
         server/routes/cms.js (ana-manset endpoints)
Current Model: Dual-list system with carousel_layout table

WHY IT OCCURS:
- Articles can have 'ana-manset' in targettedViews but NOT be in the 
  actual headline list (carousel_layout table with id='ana-manset')
- When limit of 25 is reached, oldest articles are DROPPED from the list
- BUT the 'ana-manset' target is NOT automatically removed from those articles
- Result: Article shows "ana-manset" tag but doesn't appear in manşet widget
- Dropping logic in cms.js lines 837-848 tries to clean up but can fail silently

HOW TO SOLVE:
1. Implement transactional update: When dropping articles from headline list,
   ALWAYS remove the target from article's targettedViews in same operation

2. Add validation on dashboard load to check consistency:
   - All articles in headline list should have matching targettedViews
   - All articles with 'ana-manset' target should be in the list

3. Create a cleanup script/API endpoint to fix inconsistencies

4. Add user notification when articles are auto-dropped from manşet

PROBLEM #3: DUPLICATE DataService INSTANCES (Memory/Consistency Issue)
-------------------------------------------------------------------------------
Location: Multiple files create separate DataService instances
  - server/routes/pages.js (line 19): new DataService()
  - server/routes/api.js (line 6): new DataService()  
  - server/routes/cms.js (line 32): new DataService()
  - workers/dha-rss-worker.js (line 47): new DataService()
  - server/index.js (line 212): uses Database directly for sessions

WHY IT OCCURS:
- Each file imports and instantiates its own DataService
- Each instance opens its own database connection to same SQLite file
- SQLite WAL mode helps, but still creates unnecessary overhead
- In-memory caches within each instance can become inconsistent

HOW TO SOLVE:
1. Create shared singleton pattern:
   ```javascript
   // server/services/data-service-singleton.js
   const DataService = require('./data-service');
   module.exports = new DataService();
   ```

2. All routes import the singleton instead of creating new instances

3. For testing, keep the current pattern with dependency injection

PROBLEM #6: CAROUSEL DATA SOURCE INCONSISTENCY
-------------------------------------------------------------------------------
Location: 
  - server/routes/pages.js (lines 102-133): Homepage carousel logic
  - server/routes/cms.js (lines 1122-1144): GET /carousel endpoint
  - server/services/data-service.js: getCarouselArticles vs getArticles

WHY IT OCCURS:
- Carousel has TWO data sources that can conflict:
  1. Manual list: carousel_layout table (ordered, user-controlled)
  2. Automatic: Articles with 'carousel' in targettedViews
  
- Frontend CMS uses manual list (getCarouselArticles)
- GET /cms/carousel endpoint fetches from targettedViews filter
- Homepage uses manual list if populated, else falls back to targettedViews
- Articles can be removed from manual list but still have 'carousel' target

HOW TO SOLVE:
1. Choose single source of truth - recommend manual list only
2. When article is removed from manual carousel list, also remove 
   'carousel' from its targettedViews
3. Sync both sources on CMS load to detect inconsistencies
4. Add clear documentation on which source controls what

PROBLEM #7: O(n) SLUG LOOKUP PERFORMANCE
-------------------------------------------------------------------------------
Location: server/services/url-slug.js, lines 165-172 (getIdBySlug method)

WHY IT OCCURS:
- getIdBySlug() iterates through ENTIRE slugMap to find articleId
- As article count grows, this becomes slower
- Every article page request calls this method

CURRENT CODE:
```javascript
getIdBySlug(slug) {
  for (const [id, cachedSlug] of this.slugMap.entries()) {
    if (cachedSlug === slug) return id;
  }
  return null;
}
```

HOW TO SOLVE:
1. Maintain reverse lookup Map:
   ```javascript
   this.slugMap = new Map();      // articleId -> slug
   this.reverseMap = new Map();   // slug -> articleId
   ```

2. Update both maps in getSlugForArticle, updateSlug, deleteSlug

3. Use reverseMap.get(slug) for O(1) lookup

PROBLEM #10: RACE CONDITION IN HEADLINE LIST UPDATES
-------------------------------------------------------------------------------
Location: server/services/data-service.js (addArticleToHeadlineList method)
         server/routes/cms.js (PUT /articles/:id/targets)

WHY IT OCCURS:
- Multiple CMS users could add articles to headline at same time
- getHeadlineList → modify array → updateHeadlineList is not atomic
- Between get and update, another request could modify the list
- Result: One request's changes get overwritten

HOW TO SOLVE:
1. Use SQLite transaction for the entire operation:
   ```javascript
   addArticleToHeadlineListAtomic(listId, articleId, limit) {
     const updateInTransaction = this.db.transaction(() => {
       // All operations here
     });
     return updateInTransaction();
   }
   ```

2. Or implement optimistic locking with version number

PROBLEM #12: MEMORY LEAK POTENTIAL IN WORKER MANAGEMENT
-------------------------------------------------------------------------------
Location: server/index.js, lines 35-37, 319-357

WHY IT OCCURS:
- childProcesses array stores spawned worker processes
- Cleanup happens in shutdownScheduler() on SIGINT/SIGTERM

- Child processes could become orphaned zombies

HOW TO SOLVE:

2. Add process.on('uncaughtException') handler
3. Set detached: false in spawn options (already done)
4. Consider using proper process manager (PM2) in production

5. ARCHITECTURE CONCERNS
================================================================================

-------------------------------------------------------------------------------
CONCERN #1: SINGLE PROCESS ARCHITECTURE LIMITATIONS
-------------------------------------------------------------------------------
Current Model: Single Express server with in-memory caches

ISSUES:
- Slug cache is process-local, not shared
- Cannot run multiple server instances (horizontal scaling impossible)
- RSS worker runs as child process with its own memory space
- No message passing between server and worker

RECOMMENDATIONS:
1. For horizontal scaling: Use Redis for shared caching
2. Or use database-backed caching (slug table in SQLite)
3. Consider worker process communication (IPC or message queue)

-------------------------------------------------------------------------------
CONCERN #2: NO DATABASE MIGRATIONS SYSTEM
-------------------------------------------------------------------------------
Current Model: Ad-hoc migration in migrateSchemaIfNeeded()

ISSUES:
- No version tracking for migrations
- Migrations re-run on every server start
- No rollback capability
- Hard to manage schema changes across environments

RECOMMENDATIONS:
1. Implement migration versioning (migrations table)
2. Create numbered migration files
3. Track which migrations have been applied
4. Consider using a migration library (knex, umzug)

-------------------------------------------------------------------------------
CONCERN #3: TESTING DATABASE ISOLATION
-------------------------------------------------------------------------------
Current Model: DataService throws error if no instance in test environment

ISSUES:
- Good that production DB is protected
- But setup is complex for test writers
- Each route file needs its own dataService injection

RECOMMENDATIONS:
- Already well-designed for dependency injection
- Document test setup patterns clearly
- Consider creating test helpers for common setup

SECURITY #1: HARDCODED SESSION SECRET
-------------------------------------------------------------------------------
Location: server/index.js, line 222

CURRENT CODE:
```javascript
secret: process.env.SESSION_SECRET || 'uha-secret-key-change-in-prod',
```

RISK: If SESSION_SECRET env var is not set, default secret is used
IMPACT: Session cookies could be forged if secret is known

HOW TO SOLVE:
1. Require SESSION_SECRET in production:
   ```javascript
   const secret = process.env.SESSION_SECRET;
   if (!secret && process.env.NODE_ENV === 'production') {
     throw new Error('SESSION_SECRET environment variable is required');
   }
   ```

2. Generate strong random secret for deployment
